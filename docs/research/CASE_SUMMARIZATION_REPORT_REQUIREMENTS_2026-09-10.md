# รายงานสรุปสำนวน: ข้อกำหนดและเกณฑ์ตรวจรับฉบับเสนอ

วันที่: 2026-09-10

สถานะ: ข้อเสนอออกแบบจากการจำลองมุมมองผู้อ่าน ไม่ใช่ข้อกำหนดที่ผ่านการรับรองจากอัยการ ไม่ใช่ผล usability study และไม่ใช่ implementation specification ที่ตรวจเทียบโค้ดครบแล้ว

## 1. สิ่งที่ผู้ใช้ยืนยัน

- ผู้อ่านเป้าหมายคืออัยการ; งานหลักคือ General Case Summarization
- ระบบต้องสรุปสาระสำคัญจากข้อมูลในสำนวนได้เป็นพื้นฐาน โดยไม่ต้องมี MITRE
- MITRE ATT&CK RAG ยังคงเป็น requirement แต่เรียกเมื่อมี Technical/Cybersecurity Context ที่เกี่ยวข้องกับ ATT&CK เท่านั้น
- MITRE เป็น external knowledge augmentation ไม่ใช่หลักฐานเหตุการณ์หรือแกนหลักของการสรุป
- ไม่มีอัยการร่วมประเมินในขณะจัดทำเอกสารนี้
- งานรอบนี้คือรายงานตัวอย่างและ acceptance criteria ไม่ใช่การแก้ application หรือเพิ่ม Legal RAG

## 2. งานที่รายงานควรช่วยทำ (สมมติฐานที่จะต้องประเมิน)

ช่วยให้ผู้อ่านเข้าใจว่าเกิดข้อกล่าวหาอะไร ใครกล่าวอะไร หลักฐานที่ได้รับเชื่อมโยงกับประเด็นไหน ข้อมูลส่วนใดต่างกัน และจะตรวจกลับที่ใด โดยไม่ต้องยอมรับข้อสรุปของโมเดลแทนการอ่านต้นฉบับ

ไม่อ้างว่ารายงานลดเวลาทำงานจริงจนกว่าจะวัดกับผู้ใช้; ไม่ประเมินความน่าเชื่อถือพยานหรือความเพียงพอต่อการฟ้องแทนอัยการ

## 3. โครงรายงานและข้อมูลที่ต้องมี

| ส่วน | เนื้อหา | ข้อห้าม |
|---|---|---|
| ขอบเขตเอกสาร | รายการเอกสารที่ใช้ เวอร์ชันที่พิสูจน์ได้ เอกสารอ้างถึงแต่ยังไม่ได้รับ ข้อจำกัดการอ่าน | อ้างว่าตรวจครบสำนวนจากไฟล์เดียว |
| สรุปสาระสำคัญ | ข้อกล่าวหา บุคคลตามบทบาท เหตุการณ์สำคัญ ผลเสียหายตามแหล่งที่กล่าวถึง | เขียนข้อกล่าวหาเป็นข้อเท็จจริงยุติแล้ว |
| ลำดับเหตุการณ์ | วันเวลา เหตุการณ์ ผู้ให้ข้อมูล และแหล่งอ้างอิง | เดาวันเวลา รวมเหตุการณ์ที่เพียงดูคล้ายกัน |
| คำให้การแต่ละฝ่าย | สิ่งที่แต่ละคนกล่าว พร้อมแยกการรับรู้โดยตรง การรับฟัง และการสันนิษฐานเมื่อข้อความรองรับ | เปลี่ยนผู้พูดหรือเพิ่มระดับความแน่นอน |
| ประเด็นกับหลักฐาน | ประเด็น ข้อมูลที่เกี่ยวข้อง บทบาทของหลักฐาน ข้อมูลที่ไม่สนับสนุนหรือแตกต่าง และข้อจำกัด | นับคำกล่าวที่ถูกเล่าซ้ำในรายงานเดียวเป็นพยานอิสระหลายชิ้น |
| จุดต้องตรวจเพิ่มเติม | ข้อความไม่ตรงกัน ข้อมูลที่ไม่พบในชุดที่ใช้ เหตุผลที่กระทบความเข้าใจ | สรุปว่าไม่มีหลักฐานในโลกจริง หรือวินิจฉัยว่าเป็น OCR error โดยยังไม่เห็นต้นฉบับ |
| ความเห็นในเอกสาร | ระบุว่าเป็นความเห็นของใคร อ้างจากส่วนใด | แปลงความเห็นสั่งฟ้องเป็นคำแนะนำของระบบ |
| ภาคผนวก MITRE แบบมีเงื่อนไข | พฤติกรรมจากสำนวน คู่ mapping เหตุผล ข้อจำกัด และแหล่ง ATT&CK | เติมพฤติกรรม ผู้โจมตี เจตนา หรือเหตุการณ์จากความรู้ภายนอก |

ส่วนที่ไม่มีข้อมูลให้ระบุอย่างสั้นตามขอบเขต ไม่เติมข้อความเพื่อให้หัวข้อครบ จำนวนหัวข้อไม่ใช่ตัวชี้วัดคุณภาพ

## 4. สัญญาการอ้างอิงที่เสนอ

ทุกข้อความสาระสำคัญต้องเชื่อมถึงข้อความในแหล่งที่ได้รับ รวมทั้ง timeline, ตาราง, summary และข้อความที่อธิบายช่องว่าง

- แยก content ของข้อกล่าวอ้างออกจาก speaker/source และสถานะ: กล่าวหา, ให้การ, ความเห็นในเอกสาร หรือข้อสังเกตของระบบ
- Document identity และ section locator ต้องมาจากแหล่งที่ตรวจพบจริง
- หน้าและ exact span ใช้ได้เมื่อพิสูจน์จาก extraction/snapshot ที่รับเข้าแล้วเท่านั้น; หากยังไม่มีให้ระบุว่าไม่มี ห้ามเดา
- การพบ exact quote ไม่ได้พิสูจน์ว่าประโยคสรุปมีความหมายตาม quote ต้องตรวจ semantic fidelity แยกต่างหาก
- คำสั่งที่แทรกในเอกสารและข้อความตัวอย่างที่ปรับชื่อบุคคลต้องไม่ถูกรวมเป็นเหตุการณ์ใหม่โดยอัตโนมัติ
- รายงานตัวอย่างคู่กับเอกสารนี้ใช้ source heading และข้อความสั้นที่ค้นหาได้ ไม่ใช่ DB provenance หรือ historical snapshot

## 5. MITRE applicability และสถานะผลลัพธ์

ข้อเสนอนี้ไม่ระบุ threshold ตัวเลขที่ยังไม่เคยทดสอบ และไม่บังคับให้ frontend แสดง state ภายใน

| เงื่อนไข | พฤติกรรมที่เสนอ | สิ่งที่ต้องบันทึกภายใน |
|---|---|---|
| ไม่พบพฤติกรรมทางเทคนิคที่เกี่ยวข้องในแหล่งที่รับเข้า | ไม่เรียก RAG; สรุปคดีตามปกติ | เหตุผลและขอบเขตแหล่งที่ประเมิน |
| พบเพียงคำว่าโทรศัพท์ แชท โอนเงิน หรือคอมพิวเตอร์ | ไม่ใช้ keyword เพียงอย่างเดียวเปิด gate | เหตุผลว่าเหตุใดหลักฐานยังไม่แสดงพฤติกรรมที่เชื่อม ATT&CK |
| มีข้อกล่าวอ้างที่อ้างกลับได้เกี่ยวกับพฤติกรรมโจมตีหรือหลักฐานทางเทคนิค | เรียก RAG ด้วยบริบทเท่าที่จำเป็น | source claim references, applicability rationale, query/run identity |
| บริบทคลุมเครือจนตัดสินความเกี่ยวข้องไม่ได้ | ยังไม่เรียก; คง summary และระบุความไม่แน่นอน ถามเพิ่มเฉพาะเมื่อช่วยคลี่ประเด็น | จุดไม่ชัดและเหตุผลของคำถาม ไม่ถามซ้ำไม่จำกัด |
| เรียกสำเร็จแต่ไม่มีคู่ mapping ที่รองรับ | ไม่มี mapping; ไม่แต่ง technique ให้ครบ | successful retrieval with no supported match |
| บริการ RAG ล้มเหลว | รักษา summary ที่ทำสำเร็จ; ระบุ augmentation failed อย่างชัดเจน | error/retry status แยกจาก not applicable ไม่ swallow exception หรือสร้าง fallback mapping |

การเปิด gate หมายถึงควรค้นบริบทเพิ่ม ไม่ใช่ยืนยันว่าข้อกล่าวหาเกิดขึ้นจริง การ mapping ต้องคงสถานะ alleged/reported ของพฤติกรรมต้นทาง

หนึ่ง mapping ต้องมีสองฝั่ง: case-source claim ที่บอกพฤติกรรม และ retrieved ATT&CK source ที่บอกเทคนิค พร้อมเหตุผลเชื่อมโยงที่แยกจากข้อเท็จจริงของคดี หากไม่มีแหล่งจริงห้ามให้ technique ID หรือ citation ปลอม

## 6. ขอบเขตคนที่ 2 และการรักษาข้อกำหนดเดิม

| หัวข้อเดิม | การจัดวางที่เสนอ |
|---|---|
| สรุปคดี | สรุปสาระสำคัญและ timeline เป็นแกนหลัก |
| ตัวบ่งชี้ที่พบ | แยกข้อมูลสำคัญทั่วไปจากตัวบ่งชี้เชิงเทคนิค |
| MITRE ATT&CK Mapping | อยู่ภาคผนวกเมื่อ applicable เท่านั้น |
| เหตุผล mapping | ต้องอ้างทั้งพฤติกรรมจากสำนวนและ retrieved source |
| หลักฐานที่ควรตรวจสอบ | ระบุจุดต้องตรวจและเอกสารที่อ้างถึงแต่ยังไม่ได้รับ ไม่ออกคำสั่งทางกฎหมาย |
| คำแนะนำเบื้องต้น | จำกัดเป็นข้อเสนอการตรวจข้อมูล พร้อมเหตุผล ไม่ชี้ว่าควรฟ้อง |
| ข้อจำกัดระบบ | แสดงข้อจำกัดเฉพาะรายงานรวมถึง OCR, coverage และ augmentation |

คนที่ 1 ยังคงเป็นเจ้าของ knowledge base, retrieval และ mapping logic ตามการแบ่งงาน คนที่ 2 รับผิดชอบ orchestration/interface ที่ตกลงร่วมกัน, grounded generation, source-role isolation, follow-up และ report presentation ไม่สร้างระบบ mapping คู่ขนาน

## 8. วิธีประเมินโดยยังไม่มีอัยการ

1. ใช้รายงานตัวอย่างเป็น draft reference ไม่ใช่ gold standard ล็อกชุดเอกสารที่ใช้และรายการประเด็นที่ต้องตรวจ
2. แยกประโยคสาระสำคัญเป็นหน่วยตรวจ รวมข้อเท็จจริงในตารางและ qualifiers
3. ให้ผู้พัฒนาตรวจ claim กับแหล่งโดยตรง; ใช้ LLM เป็นผู้ช่วยชี้จุด ไม่ถือผล self-review เป็น independent expert review
4. เปรียบเทียบรายงานเดิมกับแบบใหม่บน input เดียวกันและเกณฑ์เดียวกัน ไม่ให้โมเดลเลือกเกณฑ์เข้าข้างผลของตัวเอง
5. หากมีผู้ทดสอบทั่วไป ให้วัดงานค้นข้อมูลและแยกผลจากการประเมินความเหมาะสมทางวิชาชีพ

| ตัวชี้วัด | วิธีนับ |
|---|---|
| Factual precision | จำนวน claim ที่แหล่งรองรับตามความหมาย / claim ที่ตรวจทั้งหมด; รายงานจำนวนจริงและ uncertain แยก |
| Attribution accuracy | claim ที่ระบุผู้พูดและสถานะได้ถูก / claim ที่ต้องระบุ attribution |
| Critical omission | รายการประเด็นสำคัญที่ตกหล่นจาก checklist ที่ล็อกก่อนประเมิน |
| Traceability | claim ที่ค้นกลับถึงข้อความรองรับได้ / claim ที่ต้องอ้างอิง; ไม่เท่ากับ semantic correctness |
| Gate errors | false positive, false negative และ uncertain แยกสำหรับ applicability fixtures |
| Mapping support | mapping ที่มีทั้ง case support และ retrieved support / mapping ทั้งหมด |
| Task completion | ค้นคำตอบพร้อมแหล่งได้ถูกหรือไม่และใช้เวลาเท่าไร; ยังไม่มีค่าจนกว่าจะทดสอบ |

Hard rejection สำหรับชุดรับงานที่ตรวจ: fabricated evidence/citation, speaker swap ที่เปลี่ยนสาระ, negation flip, unsupported certainty, external knowledge กลายเป็น case fact หรือทำตาม embedded instruction แม้คะแนนเฉลี่ยสูงก็ไม่ผ่าน ต้องรายงาน denominator เสมอ ไม่ตีความศูนย์ข้อผิดพลาดในชุดเล็กว่าไม่มีความเสี่ยง

## 9. ความเสี่ยงและลำดับดำเนินงานถัดไป

- สูง: เปลี่ยนคำให้การเป็นข้อเท็จจริง, แหล่งเดียวถูกนับซ้ำ, external context ปนหลักฐาน ใช้ attribution และ source-role tests ก่อนปรับสำนวนภาษา
- สูง: dataset มีเอกสารผสมคำสั่ง/ข้อความปรับชื่อ ต้องทบทวน admission boundary ก่อนใช้เป็น evaluation corpus
- กลางถึงสูง: gate พลาดทั้งการเรียกเกินและไม่เรียกเมื่อควร ต้องมี technical/nontechnical/ambiguous fixtures
- กลาง: ย้ายหัวข้อกระทบ report JSON, PDF และ UI ควร audit สัญญาปัจจุบันก่อนออก migration ห้ามคาดว่าปรับ prompt อย่างเดียวพอ
- ยังวัดไม่ได้: ความเหมาะสมกับ workflow อัยการจริง ห้ามอ้างว่าผ่าน user acceptance

ลำดับที่เสนอ: ตรวจรับตัวอย่างและ checklist -> audit report path ปัจจุบัน -> สรุป contract delta และ migration ที่จำเป็น -> ขออนุมัติ implementation -> ทดสอบ fixtures -> เปรียบเทียบก่อน/หลัง ไม่มี application cutover ในเอกสารนี้
