1. เหตุผลและที่มา

อาจารย์ที่ปรึกษาเสนอว่า การวัดผลระบบด้วยชุดข้อมูลที่สร้างขึ้นเองไม่เพียงพอต่อการยืนยันคุณภาพ เพราะไม่มีจุดอ้างอิงภายนอก จึงควรทดสอบด้วย ชุดข้อมูลและตัวชี้วัดชุดเดียวกับงานวิจัยที่ตีพิมพ์แล้ว เพื่อให้ตัวเลขของเราอยู่ในตารางเดียวกับเขาและตีความได้ทันที

ขอบเขตที่ต้องระบุให้ชัด

โจทย์ของเขาเป็นการติดป้ายกำกับข้อความสั้น (80–400 ตัวอักษร) ส่วนโจทย์ของเราคือ สำนวนคดีภาษาไทยขนาดยาว → รายงานสรุปเชิงโครงสร้างสำหรับพนักงานอัยการ สิ่งที่เทียบกันได้จริงคือส่วนการค้นคืนและการระบุเทคนิค ไม่ใช่ผลผลิตปลายทาง ข้อจำกัดนี้ต้องระบุทุกครั้งที่อ้างตัวเลข

นอกจากนี้ ทุก arm ของเราเป็น zero-shot ไม่ได้ฝึกกับ train split ของชุดข้อมูลเหล่านี้ ขณะที่ตัวเลขพาดหัวของ TechniqueRAG มาจากโมเดลที่ fine-tune แล้ว การเทียบที่เป็นธรรมจึงต้องเทียบกับแถว zero-shot และแถว retriever สำเร็จรูปของเขา

2.2 การพิสูจน์ว่าตัวชี้วัดตรงกับต้นทาง

การเขียนสูตร P/R/F1 ขึ้นเองไม่เพียงพอ เพราะ F1 มีหลายรูปแบบและต่างกันเล็กน้อยก็เทียบไม่ได้ จึงนำฟังก์ชันจาก evaluate.py ของต้นทางมาเป็นตัวอ้างอิง (เก็บไว้นอก repo เพื่อไม่ให้ปนสัญญาอนุญาต GPL) แล้วป้อนข้อมูลสุ่ม 400 ชุดเข้าทั้งสองฝั่ง

ผล: Precision, Recall และ F1 ตรงกันทุกชุด คลาดเคลื่อนไม่เกิน 1e-12 ทั้งสองโหมด

ข้อสังเกตของโปรโตคอลต้นทางที่ต้องทำตามให้ตรง มิฉะนั้นตัวเลขจะเทียบไม่ได้

ประเด็นพฤติกรรมของต้นทางการจัดการ
การคำนวณ F1คำนวณจากค่าเฉลี่ยของ P และ R ไม่ใช่เฉลี่ย F1 รายตัวอย่างทำตามทุกประการ และรายงาน micro-F1 เพิ่มเป็นตัวเทียบ
โหมดปริยาย--mode technique ยุบ sub-technique ขึ้นเป็น parentรายงานทั้งสองโหมด และระบุกำกับเสมอว่าตัวเลขมาจากโหมดใด
MRRคำนวณหลัง list(set(preds)) ซึ่งทำลายลำดับ และ Python สุ่ม hash ของ string ต่อ process จึงให้ค่าไม่คงที่ระหว่างการรันรายงาน MRR จากลำดับจริง พร้อมระบุว่าตัวชี้วัดนี้เทียบตรงไม่ได้

5. สรุปผล

ข้อค้นพบที่ 1 — ระบบค้นคืนของเราอ่อนในฐานะตัวจัดอันดับ แต่แข็งในฐานะตัวสร้างตัวเลือก

P@1 อยู่ที่ 0.373 ต่ำกว่าทุก baseline ที่ตีพิมพ์ แต่เมื่อพิจารณาทั้งลิสต์ 20 อันดับ เฉลยปรากฏอยู่ใน 83.3% ของตัวอย่าง (recall 0.805) แปลว่าปัญหาไม่ใช่การค้นไม่เจอ แต่เป็นการเรียงลำดับผิด

สาเหตุเชิงโครงสร้างที่ต่างจากเขา: corpus ของ TechniqueRAG คือบทสรุปรายเทคนิคที่เขียนขึ้นใหม่ และตัวอย่างที่มีเฉลยจาก train split ขณะที่ของเราเป็นคำอธิบาย STIX ดิบจากกราฟความรู้ทั้งกราฟ ซึ่งเป็นกองข้อมูลที่ค้นยากกว่ามากสำหรับข้อความชนิดนี้

ข้อค้นพบที่ 2 — การกรองให้เหลือเฉพาะ technique ไม่ช่วยเรื่องการจัดอันดับ

สมมติฐานเริ่มต้นคือผลลัพธ์ประเภท Group / Software แย่งตำแหน่งต้นตาราง แต่เมื่อวัดจริง P@1 แทบไม่เปลี่ยน (0.373 เทียบกับ 0.384) เพราะกลไกถ่วงน้ำหนักตามชนิดโหนดได้ดัน technique ขึ้นก่อนอยู่แล้ว การกรองให้ผลเฉพาะด้านความลึก คือ recall เพิ่มจาก 0.667 เป็น 0.805

ข้อค้นพบที่ 3 — การเพิ่ม retrieval ทำให้คำตอบแย่ลง

เป็นข้อค้นพบที่สำคัญที่สุดของการทดลองนี้ การนำ context ที่ค้นได้ไปประกอบคำตอบ ทำให้ F1 ลดลง 6.8 จุด (0.693 → 0.625) และลดลงทั้ง precision และ recall จึงไม่ใช่การแลกเปลี่ยนระหว่างสองค่า

6. ข้อจำกัดของการทดลองนี้

  • ตัวเลขทั้งหมดในรายงานฉบับนี้มาจาก arm ที่เป็น ablation ยังไม่ใช่ตัวเลขของ pipeline ที่ให้บริการจริง arm agent ได้พัฒนาเสร็จแล้วแต่ยังไม่ได้รัน
  • วัดบนชุด TRAM เท่านั้น ยังไม่ได้วัด Expert (multi-label) และ Procedures
  • การเทียบ rag-en กับแถว RAG ของงานตีพิมพ์ ปนตัวแปรสองอย่างคือตัวค้นคืนที่ต่างกันและโมเดลภาษาที่ต่างกัน แยกออกจากกันไม่ได้
  • MRR ไม่สามารถเทียบกับต้นทางได้ ด้วยเหตุผลที่ระบุในหัวข้อ 2.2

7. งานที่ควรทำต่อ

ลำดับงานเหตุผลต้นทุนโดยประมาณ
1รัน arm agent บนชุด Expert ได้ตัวเลขของ pipeline จริงตามหลักการ และ Expert เป็น split เดียวที่มี P@1 / P@3 ที่ตีพิมพ์ให้เทียบตรง ~45 นาที · ~$0.30
2ทดลองแก้ถ้อยคำใน prompt เปลี่ยนจาก “ใช้ข้อมูลที่ค้นมาเป็นหลักฐาน” เป็น “ใช้เมื่อเป็นประโยชน์” เพื่อแยกว่าที่เสีย 6.8 จุด เกิดจาก prompt ที่บังคับ หรือจากคุณภาพ candidate — หากเป็นอย่างแรก แก้ได้ทันทีบน production ~20 นาที · ~$0.35
3ทดสอบผลของการแตกคำถามย่อยบนชุด Expert TechniqueRAG แตกคำถามย่อยอยู่ภายใน prompt ของ re-ranker การไม่ทำจึงเป็นการเสียเปรียบบน split ที่เป็น multi-label ~15 นาที · ~$0.05
4แก้การรวมคะแนนข้าม collection การ normalize แบบ min-max แยกตาม collection บังคับให้อันดับหนึ่งของแต่ละ collection มีค่าเท่ากับ 1.0 เสมอ ไม่ว่าจะเกี่ยวข้องจริงหรือไม่ กระทบการค้นคืนของ production ทั้งระบบ ต้องวัดก่อนและหลัง
5พิจารณา fine-tune เพื่อเทียบกับตัวเลข 0.740 โครงการมีโมดูล fine-tune อยู่แล้ว การฝึกบน train split ของ TRAM จะทำให้เทียบกับตัวเลขพาดหัวของเขาได้อย่างเป็นธรรม เป็นงานแยกอีกก้อน
