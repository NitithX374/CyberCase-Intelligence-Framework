CyberCase Intelligence Framework  ·  branch eval/published-baselines  ·  30 commits
ขอบเขต: สร้างชุดทดสอบเทียบกับงานวิจัยที่ตีพิมพ์ · วัดผล pipeline · แก้ข้อบกพร่องที่พบระหว่างการวัด

ผลสรุปสามข้อ

1. วัด pipeline ที่ให้บริการจริงได้เป็นครั้งแรก — บนสำนวนคดีไทย F1 0.746 (gpt-5.6-luna) และ 0.576 เมื่อเปลี่ยนเป็นโมเดลเปิดขนาด 9B

2. ผลของแต่ละองค์ประกอบกลับด้านตามภาระงาน การค้นคืนและ re-ranker ทำให้แย่ลงบนชุดทดสอบภายนอก แต่ทำให้ดีขึ้นชัดเจนบนโจทย์จริง — วัดได้ทั้งสองทิศทางในการทดลองเดียวกัน

3. พบและแก้ข้อบกพร่องใน production 6 จุด ทั้งหมดเป็นชนิดที่ไม่ทำให้ระบบพัง จึงไม่มีใครเห็นจนกระทั่งรัน pipeline จริง

ตำแหน่งของช่องว่างบอกอะไรมากกว่าขนาด — recall ต่าง 0.222 (0.813 เทียบ 0.591) ขณะที่ precision ต่างไม่ถึงครึ่งหนึ่งของนั้น ทั้งสองได้ context ชุดเดียวกันเป๊ะ โมเดลเล็กจึงไม่ได้ถูกจำกัดด้วยการค้นคืน แต่สกัดเทคนิคที่ถูกออกจาก context เดียวกันได้น้อยกว่า คอขวดอยู่ที่การอ่าน context ยาว มิใช่ที่ตัวค้นคืน

ข้อความที่เขียนได้: “บน pipeline และชุดข้อมูลเดียวกัน โมเดลเปิดขนาด 9B ทำได้ F1 0.576 เทียบกับ 0.746 ของโมเดลเชิงพาณิชย์ คิดเป็น 77% ของสมรรถนะ โดยมีค่าใช้จ่ายด้าน output ต่ำกว่า 8 เท่า และติดตั้งภายในองค์กรได้ ซึ่งเป็นข้อกำหนดของงานที่ประมวลผลสำนวนคดี” — เป็นข้อโต้แย้งเรื่องการแลกเปลี่ยน มิใช่เรื่องคุณภาพที่เท่ากัน

3. ข้อบกพร่องที่พบและแก้

ทั้งหกจุดมีลักษณะร่วมกัน คือไม่ทำให้ระบบพัง จึงไม่ปรากฏจนกระทั่งมีการวัดผล pipeline จริง สี่จุดแรกเป็นผลจากการเปลี่ยนสถาปัตยกรรมแล้วเก็บของเดิมไว้โดยปิดทับแทนการรื้อ

จุดอาการการแก้ไข
router จำแนกประเภทคำถามทุกครั้งแล้วทิ้งผลลัพธ์ — เส้นเชื่อมถูกกำหนดตายตัวเป็นเส้นทางเดียว ทำให้เสีย LLM call ฟรีทุกคำถาม ถอดออกจาก graph ทั้งหมด · ประหยัด 1 call ต่อคำถาม
prompt ขัดแย้งกันเอง สั่งทั้ง “ห้ามเขียนภาษาไทย” และ “เขียนภาษาไทยทั้งหมด” ในข้อความเดียวกัน ผลขึ้นกับว่าโมเดลแก้ความขัดแย้งทางใด — โมเดลใหญ่ทำถูก โมเดล 9B ตอบสำนวนคดีไทยเป็นภาษาอังกฤษ ทำเป็นเทมเพลตที่ระบุภาษาครั้งเดียวในกฎข้อ 1 · ทดสอบแล้วได้ภาษาไทย 100/100
ปฏิเสธที่จะตอบ ACKNOWLEDGE_LIMIT ลัดวงจร ไม่เรียก generation เลย — เกิด 40% ของ TRAM และได้ศูนย์ทุกข้อ รวมถึงข้อที่ตอบได้ชัด ส่งสิ่งที่ขาดเข้า prompt แทน ตอบเท่าที่ข้อมูลรองรับแล้วปิดท้ายด้วยหัวข้อขอข้อมูลเพิ่ม · F1 +0.149
node_label_filter รับพารามิเตอร์แล้วไม่ส่งต่อ ผู้เรียกได้ผลลัพธ์ที่ไม่ถูกกรองโดยไม่มีการแจ้งเตือน ต่อพารามิเตอร์ให้ครบ · กรองฝั่งไคลเอนต์เพราะ Qdrant ต้องมี payload index
การรวมคะแนนข้าม collection normalize แบบ min-max แยกแต่ละ collection บังคับให้อันดับหนึ่งของแต่ละฝั่งเท่ากับ 1.0 เสมอ ไม่ว่าจะเกี่ยวข้องจริงหรือไม่ เปลี่ยนเป็นรวมด้วยอันดับพร้อมน้ำหนักที่ประกาศไว้
ไม่มี timeout ไคลเอนต์ LLM รอไม่จำกัด · 1 การเรียกค้างทำให้ทั้งชุดหยุดและไม่มีอะไรถูกเขียนลงดิสก์ timeout 120 วินาทีต่อคำขอ · 180 วินาทีต่อชุด · ทิ้งตัวที่ค้างแล้วเก็บภายหลัง
พบเพิ่มเติมแต่ยังไม่แก้: gap_warning ของ PARTIAL_ANSWER เขียนลง state แล้วไม่มีใครอ่าน (แก้พร้อมข้อ 3 แล้ว) · FINAL_TOP_K = 5 ตัด context ของ LLM เหลือหนึ่งในสี่ · max_length = 512 ของ cross-encoder กำหนดตายตัวทั้งที่โมเดลรองรับ 8192

4. ข้อค้นพบเชิงวิธีการ

4.1 ชุดทดสอบภายนอกอาจวัดคนละอย่างกับที่ระบบทำ

คลังค้นคืนของ TechniqueRAG คือ procedure example ซึ่งเป็นข้อความชนิดเดียวกับคำถาม วัดการซ้อนทับคำระหว่างคำถาม TRAM กับเอกสารเป้าหมาย ได้ค่ามัธยฐาน 0.43 เทียบกับ 0.25 ของคลังนิยามเทคนิคแบบที่ระบบนี้ใช้ และสูงกว่าใน 64% ของตัวอย่าง

สถาปัตยกรรมดังกล่าวใช้กับระบบนี้ไม่ได้โดยหลักการ เพราะคำถามเป็นภาษาไทยขณะที่ฐานความรู้เป็นภาษาอังกฤษ การจับคู่คำจึงเป็นไปไม่ได้ การค้นคืนแบบ dense เป็นข้อกำหนดของโจทย์ มิใช่ทางเลือกเชิงออกแบบ

ไม่มีเหตุการณ์ใดเลยที่จัดอันดับถูกในภาษาหนึ่งแต่ผิดในอีกภาษาหนึ่ง จุดอ่อนด้านภาษาไทยจึงอยู่ที่ BGE-M3 ซึ่งเป็นตัวสร้างเวกเตอร์ มิใช่ที่ตัวจัดอันดับใหม่ เป็นตัวเลขความสามารถหลายภาษาชุดแรกของโครงการ และเป็นความสามารถที่งานคู่เทียบทั้งสามไม่มี

4.3 ข้อควรระวังเรื่องการปนเปื้อนของชุดทดสอบ

gpt-5.6-luna ตอบเองโดยไม่ใช้การค้นคืนได้ F1 0.693 บน TRAM สูงกว่าแถว zero-shot ที่ตีพิมพ์อย่างมาก (GPT-4o 0.434) และสูงกว่า qwen3.5-9b บนโจทย์เดียวกันถึง 0.39 procedure example ของ MITRE เป็นข้อมูลสาธารณะ จึงมีความเป็นไปได้สูงว่าโมเดลรุ่นใหม่เคยเห็นระหว่างการฝึก

ข้อนี้กระทบการตีความทุกงานที่วัดผลบน TRAM ด้วยโมเดลรุ่นใหม่ ไม่ใช่เฉพาะงานนี้ และบนสำนวนคดีไทยซึ่งเขียนขึ้นเองด้วยมือ ข้อกังวลนี้ไม่เกิดขึ้น

4.4 ข้อมูลฝึกกับชุดทดสอบมาจากแหล่งเดียวกัน

กราฟของโครงการมีตัวอย่างเชิงกระบวนการ 18,383 รายการซึ่งเหมาะเป็นชุดฝึก re-ranker แต่ชุดทดสอบที่ตีพิมพ์ก็สร้างจาก MITRE procedure examples เช่นกัน ตรวจพบทับซ้อน 1,656 รายการ (เฉพาะ TRAM คือ 228 จาก 725 หรือ 31.4% โดย 207 รายการมีป้ายเฉลยตรงกันด้วย)

การเทียบด้วยข้อความตรง ๆ ตรวจไม่พบเลย เพราะชุดทดสอบตัดชื่อผู้กระทำออกจากต้นประโยค ต้องเทียบบนข้อความที่ทำให้เป็นมาตรฐานแล้วและใช้การบรรจุอยู่ภายใน รายการที่ตัดออกบันทึกไว้เป็นหลักฐานตรวจสอบย้อนกลับ

5. ข้อจำกัด

  • ชุดทดสอบภาษาไทยมี 100 ตัวอย่าง ความต่างต่ำกว่าราว 0.05 ควรถือเป็นสัญญาณรบกวน ผลของตัวจัดอันดับใหม่ (+0.100) อยู่เหนือเกณฑ์นั้นสองเท่า แต่ควรยืนยันซ้ำด้วยชุดที่ใหญ่ขึ้น
  • วัดเฉพาะการระบุเทคนิค ยังไม่ได้วัดคุณภาพของรายงานปลายทาง ซึ่งเป็นผลผลิตจริงของระบบ
  • การใช้กราฟความสัมพันธ์ยังไม่ได้ประเมินแยก — ชุดทดสอบไม่มีความสัมพันธ์ระหว่าง entity ให้ใช้เพียงพอ
  • ยังไม่ได้วัด Expert และ Procedures · ยังไม่ได้รัน agent ด้วย gpt-5.6-luna เพื่อเทียบโมเดล
  • ข้อสรุปเรื่องการปนเปื้อนเป็นการอนุมานจากคะแนน มิใช่การตรวจสอบชุดข้อมูลฝึกของโมเดลโดยตรง
  • MRR เทียบกับต้นทางไม่ได้ เนื่องจากโค้ดต้นทางคำนวณหลังทำลายลำดับและให้ค่าไม่คงที่ระหว่างการรัน

6. งานที่ควรทำต่อ

#งานเหตุผลต้นทุน
1ปรับ prompt ให้โมเดลเล็กสกัดเทคนิคได้ครบขึ้น ช่องว่างระหว่างโมเดลอยู่ที่ recall (0.591 เทียบ 0.813) บน context ชุดเดียวกัน — โมเดลเล็กมองข้ามเทคนิคที่มีอยู่ใน context
ต้องระวังการปรับ prompt ซ้ำ ๆ จนเข้ากับชุดทดสอบ 100 เรื่องนี้ ควรแก้ตามเหตุผลที่วินิจฉัยได้ครั้งเดียว มิใช่ค้นหาตัวแปรที่ให้คะแนนสูงสุด		 ~1 ชม. · ~$0.10
2ปรับปรุงตัวสร้างเวกเตอร์ ช่องว่าง recall ไทย–อังกฤษ 0.126 เป็นเพดานของทั้ง pipeline · มีโมดูล embed_ab อยู่แล้ว ฟรี
3ปรับจูน re-ranker พิสูจน์แล้วว่ามีคุณค่า (+0.100 บนโจทย์จริง) จึงมีช่องให้ปรับปรุง · ชุดข้อมูล 15,915 รายการเตรียมไว้แล้ว
