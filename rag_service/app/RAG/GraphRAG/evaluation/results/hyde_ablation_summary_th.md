## 1. ที่มาของการทดลอง

จากการรีวิวโปรเจกต์ จุดอ่อนหลักที่พบคือระบบค้นคืนเทคนิคได้ไม่ดี เมื่อสำนวนคดี**บรรยายพฤติกรรม**ของคนร้ายโดยไม่ระบุชื่อเทคนิค เช่น "คนร้ายส่งคำสั่งฐานข้อมูลแทรกเข้าไปทางช่องกรอกข้อมูลบนเว็บ" แทนที่จะเขียนว่า "SQL Injection"

สาเหตุคือ query กับเอกสารในคลังเขียนคนละแบบ:

- **Query** เป็นเรื่องเล่าจากสำนวนคดีภาษาไทยว่า *เกิดอะไรขึ้น*
- **เอกสารในคลัง** เป็นคำอธิบายแบบสารานุกรมภาษาอังกฤษว่า *คนร้ายอาจทำอะไร* เช่น `Technique: Web Shell. Adversaries may backdoor web servers...`

**HyDE (Hypothetical Document Embeddings; Gao et al., ACL 2023)** แก้ปัญหานี้โดยตรง แทนที่จะค้นด้วยคำถาม ให้ LLM เขียน "เอกสารสมมติ" ที่น่าจะเป็นคำตอบก่อน แล้วค้นด้วยเอกสารนั้น

## 2. สิ่งที่ทำ

### 2.1 โค้ดที่เพิ่มหรือแก้

| ไฟล์ | การเปลี่ยนแปลง |
|---|---|
| `pipeline/hyde.py` (ใหม่) | `HydeWriter` เรียก LLM หนึ่งครั้งต่อหนึ่งคดี แล้วเขียน entry สมมติสไตล์ ATT&CK ให้ทุก sub-query ในรูป `ลำดับ \| ชื่อเทคนิค \| คำอธิบาย "Adversaries may..."` โดยแยก**ชื่อที่ LLM เดา**ออกจาก**คำอธิบายพฤติกรรม** เพื่อให้วัดได้ว่าผลดีมาจากส่วนไหน |
| `retrieval/hybrid_retriever.py` | `retrieve()` และ `retrieve_multi_quota()` รับ `search_texts` เพิ่ม ทำให้ข้อความที่ใช้ค้นแยกจาก query ที่ reranker ใช้ให้คะแนนได้ และรับ `expand_graph` เพิ่มเพื่อข้าม Neo4j ได้ ค่า default ไม่เปลี่ยน production path จึงยังทำงานเหมือนเดิม |
| `evaluation/hyde_benchmark.py` (ใหม่) | ชุดทดลองแบบ 3 phase ที่รันต่อจากจุดที่ค้างได้ (รายละเอียดด้านล่าง) |

**HyDE ยังไม่ได้ต่อเข้า `agent_graph`** ระบบที่ใช้งานจริงยังทำงานเหมือนเดิม

### 2.2 วิธีการทดลอง

ชุดทดลองแบ่งเป็น 3 phase:

1. **generate:** แยก incident เป็น sub-query (decompose) แล้วเขียน HyDE entry ทุกคดี และ cache ผลไว้ มีเฉพาะ phase นี้ที่เรียก LLM
2. **retrieve:** รันทุก arm บน sub-query และ entry ชุดเดียวกันจาก cache ผลจึงจับคู่เทียบกันได้ตรงตัว (paired) ขั้นนี้ไม่เรียก LLM
3. **report:** ทำตารางผล และคำนวณผลต่างแบบ paired เทียบกับ baseline พร้อม 95% CI จาก bootstrap 10,000 รอบ และ p-value จาก Wilcoxon signed-rank

ทุก arm ใช้โครงสร้างเดียวกับ production คือช่องแรกเป็นทั้ง incident ตามด้วยหนึ่งช่องต่อ sub-query ใช้ quota 3 ต่อ query และ round-robin ต่างกันแค่**ข้อความที่ใช้ค้น**และ**ข้อความที่ reranker ใช้ให้คะแนน**

| Arm | ค้นด้วย | Reranker เทียบกับ | ทดสอบอะไร |
|---|---|---|---|
| `quota` | sub-query | sub-query | baseline ซึ่งเหมือนระบบปัจจุบัน |
| `hyde` | HyDE entry | HyDE entry | HyDE แบบดั้งเดิม |
| `hyde_desc` | คำอธิบายอย่างเดียว | คำอธิบาย | ถ้าตัดชื่อที่ LLM เดาออก ผลเหลือเท่าไหร่ |
| `hyde_fuse` | sub-query + HyDE entry | HyDE entry | การรวมผลค้นจากทั้งสองแบบช่วยเพิ่มหรือไม่ |
| `hyde_fuse_sub` | sub-query + HyDE entry | sub-query | ให้ reranker ตัดสินด้วยถ้อยคำในสำนวนเอง ชื่อที่เดาจึงแค่เพิ่มตัวเลือก |

Metric หลักคือ **StepCoverage@K** คือสัดส่วนของขั้นตอนการโจมตีที่มี gold technique อย่างน้อยหนึ่งตัวอยู่ใน K อันดับแรก แยกดูตามประเภทขั้นตอน (บรรยายพฤติกรรม / ระบุชื่อ)

## 3. ผลการทดลอง

### 3.1 ข้อค้นพบแรก: baseline จริงสูงกว่าที่เคยรายงานมาก

ตัวเลข StepCoverage@5 ของขั้นตอนที่บรรยายพฤติกรรมที่เคยอ้างไว้คือ .105 / .159 **ตัวเลขนั้นผิด** เพราะรันตอนที่ environment ไม่มี key `OPENROUTER_CYBERCASE` decomposer จึงค้นทั้งสำนวนเป็นก้อนเดียวแทนการแยก sub-query

| StepCoverage@5 | รันเดิม (ไม่ได้แยก sub-query) | รันใหม่ (แยก sub-query จริง) |
|---|---|---|
| ขั้นตอนที่บรรยายพฤติกรรม | .159 | **.669** |
| ขั้นตอนที่ระบุชื่อเทคนิค | .831 | **.885** |
| ทุกขั้นตอน | .274 | **.697** |

ช่องว่างจริงระหว่างสองประเภทจึงประมาณ **.22** ไม่ใช่ .7 การแยก sub-query ในระบบปัจจุบันแก้ปัญหาส่วนใหญ่ไว้แล้ว

- `hyde_fuse_sub`: 15 / 84 / 1

### 3.4 การวินิจฉัย: ชื่อเทคนิคที่ HyDE เดาถูกแค่ไหน

- ชื่อที่ LLM เดามา **ถูกเพียง 34%** (precision .342)
- ชื่อที่เดาครอบคลุม gold technique 55% (recall .547)

ตัวเลขนี้นับผ่าน alias map ซึ่งจะแปลงชื่อที่ซ้ำกันระหว่าง enterprise กับ mobile เป็น ID ของ mobile ค่าจริงจึงอาจสูงกว่านี้เล็กน้อย

## 4. การตีความ

1. **HyDE ช่วยได้จริงในจุดที่ตั้งใจแก้** `hyde` เพิ่มการครอบคลุมขั้นตอนที่บรรยายพฤติกรรมประมาณ +.10 อย่างมีนัยสำคัญ ที่ K=10 ช่องว่างกับขั้นตอนที่ระบุชื่อเกือบปิดสนิท (.899 เทียบ .949)
2. **แต่ต้องแลกกับอันดับบนสุด** ค่า @1 และ MRR ลดลง และขั้นตอนที่ระบุชื่อเสียเล็กน้อย เพราะ HyDE entry เข้าไปแทนที่ชื่อเทคนิคที่สำนวนเขียนไว้อยู่แล้ว
3. **ผลดีครึ่งหนึ่งมาจากชื่อที่ LLM เดา** เมื่อตัดชื่อออก (`hyde_desc`) ผลเหลือแค่ประมาณครึ่ง ขณะที่ชื่อที่เดาถูกเพียง 34% แปลว่าบางส่วนของสิ่งที่ `hyde` ค้นได้ถูกชี้นำด้วยความรู้เดิมของโมเดล ไม่ได้มาจากสำนวนคดี ซึ่งเป็น**ความเสี่ยงด้าน grounding** ที่ต้องระวังในงานที่ผลลัพธ์ใช้ประกอบสำนวนอัยการ
4. **`hyde_fuse` ไม่เพิ่มอะไร** เมื่อ reranker ให้คะแนนเทียบกับ HyDE entry ก็เลือกผลบนสุดชุดเดิมอยู่ดี การรวมผลค้นจาก sub-query จึงเพิ่มแค่เวลา
5. **`hyde_fuse_sub` เป็นทางเลือกที่ปลอดภัย** ได้ผลน้อยกว่า `hyde` (+.038 ถึง +.057) แต่แทบไม่มีคดีที่แย่ลง และ MRR ไม่ลด เพราะ reranker ยังตัดสินด้วยถ้อยคำในสำนวนเอง ชื่อที่เดาจึงแค่เพิ่มตัวเลือก ไม่ได้เป็นตัวชี้ขาด

## 5. ข้อเสนอ

- **สำหรับ production และการเขียนวิทยานิพนธ์:** เลือก `hyde_fuse_sub` เพราะได้ผลอย่างมีนัยสำคัญโดยแทบไม่มีข้อเสีย และอธิบายได้ชัดว่าทำไมไม่ทำให้ grounding แย่ลง
- **`hyde`** รายงานไว้เป็นเพดานของ recall และใช้อภิปรายเรื่อง trade-off ระหว่าง recall กับ grounding
- **ตัด `hyde_fuse` ออก** เพราะไม่เพิ่มผลแต่ใช้เวลาค้นเป็น 2 เท่า

## 6. ข้อจำกัด

- **เป็นการวัดเฉพาะส่วนค้นคืน (retrieval-only ablation)** ไม่ได้รันผ่าน agent ที่ใช้งานจริง ยังไม่รู้ผลต่อคำตอบสุดท้าย (F1, grounding) ตัวเลขหลักในวิทยานิพนธ์ต้องมาจาก agent ตัวจริง
- **ข้าม graph expansion** เพราะทุก metric วัดที่ K ≤ 15 ซึ่งเป็นส่วน vector ล้วน (quota จำกัดไว้ที่ 15 และ id จาก graph ถูกจัดอันดับต่อท้าย)
- **คอลัมน์ latency ในรายงานใช้เทียบระหว่าง arm ไม่ได้** เพราะผลการค้นถูก cache ข้าม arm และ `quota` รันเป็นลำดับแรกตอนที่ cache ยังว่าง
- **Decomposer ไม่ deterministic** แม้ตั้ง temperature 0 แต่ในการทดลองนี้ทุก arm ใช้ sub-query ชุดเดียวกันจาก cache การเปรียบเทียบจึงยังยุติธรรม

## 7. ขั้นต่อไป

1. ต่อ `hyde_fuse_sub` เข้า `_node_retrieve` ใน `agent_graph.py` โดยมี flag เปิดปิด
2. รันวัดผลแบบ end-to-end ด้วย harness เดียวกับ agentic ablation เพื่อวัด answer F1 และ grounding คาดว่ามีค่า LLM ประมาณ $1
3. ถ้าผลยังดี ค่อยนำเข้า production แล้วเขียนผลลงวิทยานิพนธ์

## 8. วิธีรันซ้ำ

รันจาก `rag_service/app` บน Windows ต้องตั้ง `PYTHONUTF8=1` ก่อน ถ้าใน environment มีแค่ `OPENROUTER_API_KEY` ให้ตั้ง `OPENROUTER_CYBERCASE="$OPENROUTER_API_KEY"`

```bash
python -m RAG.GraphRAG.evaluation.hyde_benchmark --phase all
```

ผล generation และ ranking ของทุก arm ถูกเก็บไว้ใน `evaluation/results/hyde/*.jsonl` การสร้างรายงานใหม่จึงไม่ต้องเรียก LLM ซ้ำ:

```bash
python -m RAG.GraphRAG.evaluation.hyde_benchmark --phase report
```
